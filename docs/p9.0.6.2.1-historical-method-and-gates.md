## Metoda de recuperare temporală pe fiecare relație

1. Descărcare `relation/id/full` din API OSM read-only, fixare SHA-256 XML, identificare relație-versiune și timestamp, confruntare strictă cu aceeași relație la PBF-ul din 12 octombrie.
2. Fiecare `outer/inner` way și toate nodurile acestuia se certifică la momentul-țintă **individual**. Pentru un element al cărui ultim `version/timestamp` OSM este anterior sau egal cu momentul-țintă, versiunea curentă este identică temporal cu versiunea de la data vizată. Acest fapt se verifică pentru **toate** elementele care compun fiecare poligon, nu doar pentru relația părinte.
3. Dacă orice way/node s-a modificat ulterior, trebuie folosit `/api/0.6/way|node/id/history`, selectând ultima versiune cu `timestamp <= target`; pentru way-urile istorice se închid recursiv toate node ref-urile istorice. Imposibilitatea de a recupera versiunea înseamnă `UNRESOLVED`, nu folosirea poligonului actual ca substitut. Același lucru este valabil pentru relațiile ale căror versiuni curente diferă de cele fixate în PBF.
4. Se reconstruiesc poligoanele din coordonatele OSM brute în EPSG:4326, **fără simplificare, snapping, clipping sau reparație geometrică**, și se verifică geometria cu JSTS.
5. Geometria-rădăcină `65335` se reconstruiește direct din PBF-ul datat și se verifică SHA-256 împotriva registrului P9.0.6.2, apoi se recalculează matricea **DE-9IM** pentru toate cele 84 de relații. Gate-ul reclamă **65 disjuncte, 19 cu frontieră comună și zero erori**, conform P9.0.3, dar măsurate istoric la data fixată.
6. Se fixează în artefact per ID versiunea relației, hashul sursei XML `/full`, count-ul de way-uri și noduri selectate la timp, hashurile setului de `way(id,version,timestamp,nodeRefs)` și ale `node(id,version,timestamp,lon,lat)`, segmentele poligonului, dovada oricărei recuperări de istoric și rezultatul DE-9IM. Validatorul nu deduce control administrativ de facto din această topologie.

**Gate:** numai `84/84 RESOLVED` cu reconstruire temporală și rezultatul geometric așteptat înseamnă `PASS` la alinierea geometrică istorică; în caz contrar `PARTIAL`, cu toate ID-urile și erorile salvate. `semantic_acceptance=BLOCKED_INCOMPLETE`, `p91_import_allowed=false` indiferent de rezultat.

Nu se modifică niciun poligon ACTUAL, ierarhie juridică MD, SIRUTA/CUATM, identitate, snapshot, release gate ori resursă web. Acesta este un audit read-only separat de P9.0.6.3.

Pentru *toate* componentele necesare, ultima versiune era deja editată până la timestampul-țintă. Așadar, nu există o revizie ulterioară care să modifice componentele folosite, iar versiunea disponibilă acum reprezintă chiar versiunea de la data cerută. În acest audit, `history` API a rămas fallback pregătit, dar **0** elemente au necesitat recuperarea unei versiuni anterioare. Hashul versiunilor way și al coordonatelor/versionărilor node este salvat pentru fiecare ID, fără a simplifica sau decupa poligonul.

Rădăcina **`relation/65335`** a fost reconstruită din extrasul PBF fixat `moldova-261012.osm.pbf`, checksum verificat și geometria PBF confruntată cu evidența P9.0.6.2; **nu** a fost substituită prin geometria curentă pentru reevaluarea istorică. Predicatul topologic a fost calculat pe datele aceleiași date prin JSTS/DE-9IM; clasificarea 65/19 este identică cu rezultatul live P9.0.3, dar acum are și dovada versiunilor way/node la timestampul istoric.
