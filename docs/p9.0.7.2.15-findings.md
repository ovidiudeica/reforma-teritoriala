# P9.0.7.2.15 — reconciliere semantică OSM și două niveluri independente de acceptare

**Rezultat: 85/85 poligoane + etichete OSM acceptate ca sursă cartografică; 0/85 apartenențe de facto certificate juridic; ACTUAL și P9.1 neatinse.** Etapa oferă o soluționare *cartografică*, nu transformă relațiile OSM în unități juridice certificate. Fără contactarea autorităților de facto, emailuri, achiziții sau extrase cadastrale.

## Sursa verificată și legătura temporală

- La 16.10.2026 s-au extras în **trei cereri API OSM** toate cele **85** relații ale registrului anterior, câte 30/30/25. Fiecare răspuns HTTP 200 are număr de octeți și SHA-256 în `docs/p9.0.7.2.15-osm-tag-census.json`.
- **85/85** versiuni de relații și timestampuri sunt identice cu datele din auditul geometric certificat la timestampul Geofabrik `2026-10-12T20:21:35Z`; **zero drift**. Anterior, pentru fiecare geometrie, P9.0.6.3 certificase `PINNED_PBF_EXACT_LIVE`. Nu se reproiectează și nu se modifică vreun poligon.
- XML-ul original din API este păstrat într-un arhivă GZIP/Base64 fără pierderi: `docs/p9.0.7.2.15-raw-osm-relations.json.gz.b64`, legată prin hash de cele 85 obiecte. Etichetele sunt păstrate separat pentru a fi consultate fără parsarea XML: `docs/p9.0.7.2.15-osm-tag-census.json`.
- Toate 85: `type=boundary`, `boundary=administrative`; **84 × admin_level=8**, **1 × admin_level=4**. După `place`: **72 municipality**, **7 town**, **4 city**, **1 village**, **1 fără place**. Sunt clasificări editoriale OSM, nu definiții din legislația moldovenească.
- Atribuire obligatorie: **© OpenStreetMap contributors, ODbL**, inclusiv versiune, dată și link al relației.

## Reclasificare semantică după *rolul real înscris în OSM*

Reconcilierea reproductibilă `docs/p9.0.7.2.15-osm-semantic-reconciliation.json` (generator `docs/p9.0.7.2.15-build-osm-semantic.mjs`) clasifică strict etichetele, evitând transpunerea automată în tipuri de unități juridice:

| Rol cartografic derivat din OSM | Cazuri |
|---|---:|
| Consiliu sătesc — `сельский совет` / `sovetul sătesc` | 46 |
| Consiliu de așezare — `поселковый совет` | 3 |
| Consiliu orășenesc — `городской совет` | 1 |
| Zonă administrativă OSM `place=municipality`, tip local nespecificat | 24 |
| Oraș (limită OSM) | 3 |
| Așezare de tip `town` | 6 |
| Sat (limită OSM) | 1 |
| Municipiu `admin_level=4` | 1 |
| **Total** | **85** |

**Nu există 85 de sate.** Etichetele OSM arată preponderent *perimetre de consilii locale*, zone administrative și orașe. Chiar și în cazul relațiilor numite după un sat, perimetrul unui consiliu sătesc nu este neapărat limita vetrei acelui sat.

## Cazuri individuale rezolvate descriptiv, dar necertificate juridic

- **Bender:** `osm-r12463379` = `place=city`, `admin_level=8`, numele OSM `Бендеры`; `osm-r9581354` = `place=municipality`, `admin_level=4`, nume `Municipiul Bender`. Relațiile, versiunile, geometriile și rolurile sunt diferite. Se păstrează ambele; fără unificare ori dublare de poligoane.
- **Hlinaia:** `osm-r8291058` = `Глинойский сельский совет` (consiliu sătesc, Slobozia), `osm-r9301463` = `Глинойский поселковый совет` (consiliu de așezare, Grigoriopol). Același nume românesc **nu** înseamnă o singură entitate OSM.
- **Lunga:** `osm-r19001619` = `Лунга`, `admin_level=8`, `place=municipality`; aceasta certifică *doar eticheta OSM*. Materialele anterioare despre microdistrictul Dubăsari rămân distincte. Nu se declară sat administrativ de facto independent.
- **Cremenciug:** `osm-r1216706` = `Кременчуг`, `admin_level=8`, `place=village`. Apartenența geometrică OSM la Slobozia (1702218) și revendicarea de facto Tiraspol (1702219) se stochează în **câmpuri separate**, fără a promova apartenența juridică/administrativă.
- **Rîbnița:** `osm-r9659979` = `place=city`; această relație nu este identificată automat nici cu limita intravilanului, nici cu zona cadastrală mai largă din Decretul 116/2026.

## Contractul de acceptare pe două axe

`docs/p9.0.7.2.15-dual-acceptance-policy.json` separă:

1. **CARTOGRAFIC / `ACCEPTED_SOURCE_VERIFIED` (85/85)**: dovezi OSM, versiune, limite PBF, etichete și rol OSM. Permite numai pregătirea unei **prezentări descriptive etichetate explicit OSM**, cu sursa, versiunea și nota că aceasta *nu este* o limită aprobată juridic.
2. **JURIDIC / `BLOCKED_INCOMPLETE` (0/85)**: apartenență administrativă de facto, acte normative în vigoare, planuri aprobate, delimitări juridice. Nu autorizează atribuirea părinților juridici ori afirmarea unor frontiere legale.

Acest contract **nu înlocuiește automat** politica protejată `docs/p9.0.4.3-promotion-policy.json`, al cărei `p91_import_allowed=false` rămâne valabil. **Nu activează producția și nu modifică ACTUAL.** Aplicarea opțională în UI/overlay cere un PR **distinct**, care folosește relațiile/geometriile deja existente și arată sursa, fără a modifica jurisdicția legală a Republicii Moldova ori gate-urile P9.1.

Al **20-lea validator P9**, `docs/p9.0.7.2.15-validate.mjs`, verifică integritatea octeților XML, originalele OSM/versiunile și cele 85 geometrii, rolurile consiliilor, omonimiile, cazurile speciale și interdicțiile de promovare. Executat offline în workflow-ul P9.

**Concluzie:** problema „85 identități OSM neacceptate pentru simpla cartografiere” este eliminată în contractul de candidate; identitățile juridice de facto nu sunt declarate certificate. Încetăm să mai cerem confirmări din partea regimului de facto pentru utilizarea descriptivă a OSM.
